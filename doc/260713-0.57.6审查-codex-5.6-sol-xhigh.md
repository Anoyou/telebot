最危险的三条当前链路是：

1. **payout 异常分类后删除 claim，可形成双付**：网络调用已经产生副作用但抛出未知/非网络文本异常时，当前代码把它当“确定未送达”，删除 `sending` intent，补偿扫描随后可盲重发。
2. **kill switch 状态与覆盖范围都不完整**：本地停止和广播失败可被吞；Interaction Bot、后台 RPC 与补偿扫描又不受同一门闩约束，API/前端仍可能宣称全部停止。
3. **资金已出、台账永久少记**：Telegram payout 成功后，补偿记录先进入 `sent` 终态，随后 ActionEvent 写入走可丢弃的 circuit breaker；该写入失败不会触发补偿，也没有扫描器补账。

其余 P1 包括：支付确认票据先删后执行、同一条 Bot 消息的多个 callback 去重互撞、风控 override 丢失后静默恢复满速、LLM 成本预算 fail-open，以及关键 manager 启动失败后 readiness 假健康。

上线前建议先关闭 payout 双付窗口、补齐 kill switch 全链路门闩并修复资金台账提交边界；若 LLM 已接入付费生产账号，预算 fail-closed 同级处理。callback 去重与支付确认票据问题会直接影响已付款玩法，也应在同一周内修复。

## 3. 架构简评

当前架构的正确方向是：账号 Worker 进程隔离、payout 固定 userbot、资金发送前持久 claim、补偿记录落 PostgreSQL、Redis 默认 `noeviction` + AOF、插件 generation guard、Trace 有界队列。这些设计已经挡住多类 P0。

主要结构性风险是“控制面状态”和“真实运行态”没有统一确认协议：数据库、supervisor 内存、子进程、Redis pub/sub、前端提示各自代表一部分事实。kill switch 和启动 readiness 都因此出现假成功。

资金面的问题不是幂等 claim 缺失，而是**资金副作用与可计账事件分属两个提交边界**。`PayoutCompensation.sent` 是可靠终态，`ActionEvent` 却仍被当成可丢观测 tap；但 Ledger 又把它当作真实资金来源，语义冲突直接造成 P1。

交互面已有 CAS、dedupe 和 usage claim，但关键状态大多只在 Redis。当前实现对 Redis 故障采取不同策略：payout 限额 fail-closed，普通互动 dedupe/次数限制 fail-open，LLM 成本预算也 fail-open。需要建立明确且统一的 fail-closed 清单。

### [P1] kill switch 可返回成功并显示“全部停止”，但部分 Worker 仍继续运行

- 置信度：High
- 位置：`backend/app/api/rate_limit.py:546-572`；`backend/app/worker/supervisor.py:622-675`；`backend/app/worker/supervisor.py:690-701`；`backend/app/worker/runtime.py:2146-2194`；`frontend/src/components/layout/KillSwitch.tsx:40-48`
- 机制：API 先提交数据库 `kill_switch=true`，随后调用本地 `stop_running_workers()`。本地停止的任意异常在 API 层被空 `except` 吞掉；Redis 全局广播异常也被吞。`stop_running_workers()` 又是逐账号串行，单账号异常会中断后续账号。Worker 侧仅监听 Redis pub/sub，没有周期性读取数据库总闸；而 supervisor 读取总闸遇 DB 异常还返回 `False`。最终 API 无条件返回 `{"enabled": true}`，前端据此提示“所有账号 worker 已停止”。
- 影响：安全 / 可用性 / 正确性。紧急止损时出现 fail-open，自动回复、插件动作和其他主动操作可能继续执行。
- 复现：让一个 `_WorkerHandle.process` 的 `is_alive()`、`terminate()` 或 `kill()` 抛异常，同时阻断 Redis publish；调用 `POST /api/system/kill-switch`。预期当前接口仍 200，且异常账号之后的 Worker 未被停止。现有测试只覆盖两个下游调用都成功的情况。
- 证据：API 的两个下游操作均使用 `except Exception: pass`；批量停止是 `for aid ... await stop_worker(aid)`；Worker 的 `_listen_global` 只消费广播；前端 `onSuccess` 直接宣告全部停止。
- 修复：开启总闸必须 fail-closed。批量停止改为 `gather(return_exceptions=True)` 并设置总超时，逐个核验进程确已死亡；任一失败返回 503/明确的 `partial_failure`，前端不得显示全停。Worker 增加周期性 DB 总闸复核或带租约的控制面快照；supervisor 在无法读取总闸时拒绝新启动，而不是按关闭处理。关闭总闸则应单独报告哪些账号恢复失败。
- 回归：补“单账号停止异常不阻断其余账号”“Redis 广播失败但本地全停成功”“本地与广播都失败时接口非 2xx”“DB 读取失败拒绝新 Worker”“前端不显示假成功”测试。

### [P1] payout 已发送后 ActionEvent 可被静默丢弃，资金台账永久少一笔

- 置信度：High
- 位置：`backend/app/worker/plugins/loader.py:2912-2949`；`backend/app/services/payout_compensation.py:259-307`；`backend/app/services/action_tap.py:270-349`；`backend/app/services/action_tap.py:525-581`；`backend/app/services/ledger_service.py:270-289`
- 机制：Telegram 发送成功后先调用 `complete_payout_delivery()`，在独立事务中把补偿行提交为 `sent`。随后才调用 `_emit_userbot_action_tap()` 写可计账 `ActionEvent`。Action tap 的 DB circuit 打开时直接返回 `(None, False)`，普通 DB 写失败也只记日志并返回 `None`，不会向 loader 抛异常。因此 loader 仍返回成功，不进入 post-send bookkeeping 异常分支，也不会新增歧义补偿。`sent` 又不在 Ledger 的 open compensation 状态中，没有后续扫描补账。
- 影响：资金 / 正确性 / 可观测性。钱真实发出但收入支出、净额和运营对账永久少记；管理员可能据错误余额继续操作。
- 复现：先让任意 ActionEvent 写失败以打开 30 秒 circuit；恢复 DB 后在 circuit 窗口完成一次 payout。`PayoutCompensation` 会成为 `sent`，Telegram 消息存在，但 `action_event` 无对应 `(account_id, payout_key)`。重启/补偿扫描也不会补回。
- 证据：`complete_payout_delivery` 在 294 行提交 `sent`；`emit_action_event` 接收 `_persist_action_event` 的 `None` 后正常返回；circuit 分支 528–530 明确丢事件；资金挂账 API 只查询 open 状态。
- 修复：最小正确修复是把 `PayoutCompensation sent` 与可计账 `ActionEvent OK` 放入同一 PostgreSQL 事务，并复用 `emit_action_event(..., db=db)`；Telegram side effect 后若事务失败，保留 durable `ledger_pending/ambiguous` 状态，由扫描器按 `payout_key` 补写，不能依赖 best-effort tap。资金 ActionEvent 禁止走可丢 circuit。保持 `(account_id, payout_key)` partial unique 作为最终幂等保护。
- 回归：补“ActionEvent circuit 已打开时 payout 成功”“sent 事务后 ActionEvent commit 失败”“扫描器补齐且不重复计账”“重启后收敛”测试。

### [P1] 支付确认票据在玩法成功前永久消费，瞬时失败会吞掉已付款权益

- 置信度：High
- 位置：`backend/app/services/account_bot_runtime.py:963-974`；`backend/app/services/account_bot_runtime.py:4885-4956`；`backend/app/tests/test_account_bot.py:9373-9468`
- 机制：callback 校验付款人名称后立即通过 Redis `GETDEL` 消费确认票据，然后才检查 usage、获取 usage claim 并执行 `_execute_interaction_rule()`。执行返回 `False` 或抛异常时，票据不会恢复；再次点击只能得到“确认已被处理”。现有成功测试还明确断言票据在玩法启动后消失，但没有覆盖执行失败后的重试语义。
- 影响：资金 / 正确性。付款已经确认，但游戏、权益或后续插件动作因瞬时 RPC/DB/插件故障未启动，用户无法使用原付款票据重试。
- 复现：构造合法支付确认 ticket，让 `_execute_interaction_rule()` 返回 `False` 或首次抛出可恢复异常。第一次点击显示启动失败；第二次点击显示已处理，Redis 中 ticket 已不存在。
- 证据：`GETDEL` 位于实际执行之前；失败分支只回复文案，没有写失败状态或恢复 ticket；usage claim 的释放不等于付款 ticket 恢复。
- 修复：改为持久状态机 `pending → processing(lease) → completed`。用 Lua/CAS 原子领取短租约；业务成功后才完成票据，失败或超时释放租约。若动作本身包含资金 payout，仍由 payout_key 独立幂等，不能靠票据删除防重。
- 回归：补“首次执行 False 后可重试”“异常后租约释放”“双击只有一个执行者”“执行成功后永久完成”“Worker 崩溃后租约到期恢复”测试。

### [P1] 已配置的 LLM 成本预算在 Redis/DB 故障时仍无限 fail-open

- 置信度：High
- 位置：`backend/app/services/llm_account_budget.py:186-234`；`backend/app/services/llm_runtime.py:767-777`；`backend/app/services/llm_invoke.py:164-168`；`backend/app/worker/plugins/ai_facade.py:486-496`；`backend/app/tests/test_llm_runtime.py:519-545`

### [P1] 关键 manager 启动失败无重试，依赖恢复后 `/readyz` 仍会变绿

- 置信度：High
- 位置：`backend/app/main.py:173-204`；`backend/app/main.py:388-438`；`backend/app/worker/supervisor.py:487-516`
- 机制：supervisor、account bot manager、interaction bot manager 启动异常都只记录日志并继续 lifespan，且没有重试守护。`start_supervisor()` 在读取 active account 或 DB 总闸失败时，后台 listener/monitor 尚未创建。`/readyz` 仅 ping DB 与 Redis，不检查这些关键 manager 是否实际启动。若启动瞬间依赖短暂失败，稍后 DB/Redis 恢复，容器会健康，但自动化直到整个 Web 进程重启都不恢复。
- 影响：可用性 / 正确性。所有账号 Worker、管理 Bot 或交互 Bot 可永久离线；在线更新和编排健康检查会误判成功。
- 复现：在 Web 启动阶段暂时拒绝数据库连接，让 `start_supervisor()` 抛错；随后恢复 DB/Redis。访问 `/readyz` 返回 200，但 supervisor 无 monitor/listener，active Worker 未启动。
- 证据：三个启动点均为 catch-and-log；readiness 的 checks 只有 `db` 和 `redis`；supervisor 后台任务只在前置 DB 查询成功后创建。
- 修复：关键 manager 启动失败要么阻止 readiness，要么由统一 supervisor task 以有界指数退避持续重试；readiness 增加 `supervisor_started/account_bot_manager_started/interaction_bot_manager_started` 状态。重试必须幂等，避免同账号双 Worker/双 polling。
- 回归：补“启动时 DB 失败后自动恢复”“manager 启动失败时 readyz=503”“重复启动不产生双任务”“更新健康检查等待 manager 就绪”测试。

### [P1] payout 发送抛出未知异常时删除 durable claim，补偿可盲重发导致双付

- 置信度：Medium
- 位置：`backend/app/services/interaction/userbot_actions.py:176-191`；`backend/app/worker/plugins/loader.py:2874-2903`；`backend/app/services/payout_compensation.py:237-256`；`backend/app/services/payout_compensation.py:342-362`；`backend/app/services/payout_compensation.py:480-486`
- 机制：payout 在发送前正确写入 `PayoutCompensation(status="sending")`。但 `client.send_message()` 抛异常后，代码仅用异常类型/文本中的 timeout、network 等关键词判断是否 ambiguous；凡不匹配者都调用 `release_payout_delivery_claim()` 删除这条 durable intent。上层随后以 `telegram_api_error` 新建 `pending, ambiguous=false` 补偿，扫描器可直接重发。若 Telegram 已接受消息，但客户端在解析响应、后处理或其他未知阶段抛出非网络文本异常，同一 `payout_key` 的防重行已被删除，第二次发送不会被 claim 拦住。
- 影响：资金。窄窗口重复付款；这是本轮唯一成立的直接双付链，但利用依赖“副作用已发生 + 异常未被当前文本分类捕获”，因此定 P1 而非 P0。
- 复现：mock `send_message` 先记录一次已发送副作用，再抛 `ValueError("bad response")`；断言 `sending` 行被删除，上层创建 `pending/ambiguous=false`，补偿扫描再次调用 send。
- 证据：`_is_ambiguous_error` 只匹配有限 timeout/network marker，并把包含 `rpcerror` 的文本优先认定非歧义；release 函数直接删除 `sending` 行；`telegram_api_error` 又属于 retryable。
- 修复：任何已经进入 Telegram 网络调用的 payout 异常默认都必须保留 `sending` 并转 `ambiguous=true`；只有能够在代码结构上证明请求尚未发出（本地参数校验、实体解析前置阶段）的错误才允许 release。不要用错误字符串推断副作用是否发生。
- 回归：补“已投递后抛 ValueError/未知异常”“明确本地校验错误可释放”“FloodWait/RPCError 的发送阶段语义”“ambiguous 不自动盲发”测试。

### [P1] callback 跨管道去重键缺少 callback 身份，同消息多个按钮互相锁死

- 置信度：High

- 回归：拆分前后运行现有全套测试，并为每个模块建立独立故障注入测试。

### [P3] 一键安装入口和默认 clone 跟随 moving branch，部署不可复现

- 置信度：High
- 位置：`scripts/install-server.sh:3-13`；`scripts/install-server.sh:182-200`；`README.md:32-40`
- 机制：推荐入口直接下载 `main` 上的脚本，未指定 `TELEPILOT_BRANCH` 时 shallow clone 仓库默认分支。相同安装命令在不同时间得到不同代码，无法从安装命令本身复原版本。
- 影响：供应链可追溯性 / 运维。不是个人可信插件的 RCE 问题，但会增加回滚、事故复盘和稳定部署难度。
- 复现：在两个时间点执行相同安装命令，目标 commit 取决于当时默认分支 HEAD。
- 证据：curl URL 固定为 `/main/`；clone 未指定 tag/commit。
- 修复：发布文档优先提供版本 tag/commit 固定 URL；脚本接受并记录 `TELEPILOT_REF`，生产默认解析稳定 tag，显式 `latest/main` 才跟随移动分支。
- 回归：安装完成输出并保存精确 commit；CI 对 release 安装命令做固定 ref 校验。

### [P3] “legacy 未签名兼容”开关实际也放行新上传 ZIP，配置注释与行为不一致

- 置信度：High
- 位置：`backend/app/settings.py:84-92`；`backend/app/services/plugin_install_service.py:343-368`
- 机制：设置注释称 `plugin_allow_legacy_unsigned_plugins` 用于兼容历史 `signature_ok=NULL` 插件，并称新安装流程仍强制验签；实际 `plugin_pubkey` 为空且该开关默认 True 时，`install_zip` 会直接接受新的未签名 ZIP，记为 community trust。
- 影响：供应链提示 / 可维护性。个人可信插件模型下不构成 P0/P1，但运维可能依据注释误以为新包必须签名。
- 复现：保持默认空 pubkey 与 allow=True，上传无 signature 的新 ZIP；安装成功。
- 证据：`install_zip` 只有“配置公钥”或“allow=False”时拒绝；默认组合走免签放行。
- 修复：拆成 `allow_existing_unsigned` 与 `allow_new_unsigned_uploads` 两个显式策略；默认保留历史加载兼容，但新 ZIP 是否免签由 UI 明确确认和审计，注释与行为保持一致。
- 回归：覆盖历史 NULL 插件加载、新 ZIP 无签名、配置公钥缺签名、显式 community 安装四种矩阵。

## 5. 性能与建设性优化

以下建议不以牺牲 payout 幂等、预算约束或 kill switch 正确性为代价。

### Quick win

#### 5.1 kill switch 并行停止并设置总超时

- 现状证据：`supervisor.stop_all_workers()` 已在 `backend/app/worker/supervisor.py:583-588` 使用 `gather(return_exceptions=True)`；`stop_running_workers()` 在 672–675 仍串行。单 Worker 优雅等待最多约 5 秒，随后 terminate/join/kill。
- 假设收益：N 个账号的紧急停止从接近 N×等待时间降到接近最慢单账号；10 个卡住 Worker 可从约 80 秒量级降至约 8–10 秒。
- 风险：同时 terminate 可能造成短时 CPU/IO 峰值；需要限制并发或分批。
- 改动面：supervisor、kill switch API、前端结果展示、故障测试。
- 优先级：Quick win，且与 P1-1 同修。

#### 5.2 Worker 启动/重连增加全局 Semaphore 和 jitter

- 现状证据：`backend/app/worker/supervisor.py:499-510`、678–687 顺序快速拉起 active Worker；每个 Worker 随后建立 Telegram、Redis、DB 连接，当前没有全局建连上限。
- 假设收益：大量账号在部署、Redis 恢复或 Telegram 网络恢复时减少连接峰值、FloodWait 和 CPU/RSS 瞬时抖动。
- 风险：冷启动总时长增加；Semaphore 过小会延长恢复。
- 改动面：supervisor 启动队列、monitor retry、启动指标。
- 优先级：Quick win；建议默认并发 3–5，可配置，并为 retry 加 10%–30% jitter。

#### 5.3 装机插件补齐 Event Bus/usage 契约

- 现状证据：装机校验通过但有 6 个 legacy bridge 警告。
- 假设收益：减少每个事件的兼容分支判断，主要收益是降低维护和测试成本，延迟收益较小。
- 风险：迁移时事件列表遗漏会造成插件不触发。
- 改动面：6 个 manifest、契约验证器、插件测试。
- 优先级：Quick win。

### Structural

#### 5.4 LLM HTTP 客户端按 provider + proxy + identity 复用连接池

- 现状证据：`backend/app/services/llm_client.py:932,1047,1129,1201,1375,1518,1632,1808,1960,2093,2261` 多个 provider 路径每次创建并关闭 `httpx.AsyncClient`。
- 假设收益：减少 DNS、TCP/TLS 和代理握手；高频短请求下可明显降低首 token 延迟和 socket churn。实际收益需用 provider 维度 p50/p95 验证。
- 风险：代理/密钥/identity 热更新后复用旧 client；连接池泄漏；不同安全身份串池。
- 改动面：LLM client factory、配置 generation、应用 shutdown、指标。
- 优先级：Structural。缓存键必须包含 provider 类型、base URL、proxy、TLS/identity 配置和凭据 generation；密钥轮换时主动关闭旧池。

#### 5.5 Ledger 汇总下推 SQL，元数据改为维表/定向查询

- 现状证据：`backend/app/services/ledger_service.py:187-235` 把默认 30 天全部条目加载到 Python 聚合；471–535 为补 chat/user label 最多扫描 5000 条 EventTrace。
- 假设收益：资金流水增长后显著降低 Web 进程内存、DB→应用传输和 API p95；汇总可使用 `SUM/COUNT/GROUP BY date/chat/recipient`。
- 风险：金额方向、状态过滤和时区日界线写错会造成账表口径漂移。
- 改动面：SQLAlchemy query、可能的 chat/user label 维表、Ledger API 契约和对账测试。
- 优先级：Structural。先建立 Python 旧实现与 SQL 新实现的随机数据等价测试，再切换。

#### 5.6 互动持久 dedupe 与 Redis 快速缓存分层

- 现状证据：关键 trigger/usage 只依赖 Redis，polling offset 又是 batch 后提交。
- 假设收益：保留 Redis 热路径低延迟，同时使付款通知、session start 等状态动作在重放/重启下保持 exactly-once-effect。
- 风险：每消息都写 DB 会放大 IO；错误选择唯一键会误去重。
- 改动面：ActionEvent/source event 表、规则分类、互动路由、清理策略。
- 优先级：Structural。仅对有副作用事件持久去重；观察型事件继续 Redis TTL。

### Strategic

#### 5.7 拆分互动运行时、插件 loader 与 BotTab

- 现状证据：三个模块分别约 9006、7661、3645 行，且包含多条资金/支付/控制路径。
- 假设收益：缩小故障域，允许针对 payout、payment confirmation、polling、usage 独立压测和故障注入；长期降低 P1 回归概率。
- 风险：大规模搬迁可能改变导入、副作用初始化和共享状态；短期回归风险高。
- 改动面：后端模块边界、依赖注入、前端 hooks/components、测试 fixture。
- 优先级：Strategic。必须在 P1 修复后分阶段进行，不应与资金语义修复混成一个 PR。

#### 5.8 建立统一 fail-closed 策略表与健康状态机

- 现状证据：payout 限额 fail-closed；互动 dedupe/usage、LLM budget fail-open；kill switch 和 readiness 又把“配置已写”误当“动作已完成”。
- 假设收益：减少新功能自行选择异常语义造成的安全边界漂移；运维可以直接看到 `desired/observed/degraded`。
- 风险：过度 fail-closed 会影响纯观察功能可用性。
- 改动面：策略枚举、manager health registry、readiness、UI degraded 状态、告警。
- 优先级：Strategic。资金、总闸、鉴权、付费预算默认 fail-closed；只读观察能力允许显式 fail-open。

## 6. 最值得补的测试缺口

1. payout 异常：模拟“Telegram 已投递后抛未知异常”，断言 claim 不删除、不得盲重发。
2. kill switch：单 Worker 停止异常、Interaction Bot、RPC payout、补偿扫描组合，验证所有副作用入口都被门闩阻断。
3. callback：同一消息不同按钮均执行并 ACK，同一 callback update 重放才被去重。
4. payout 台账：Telegram 已成功、ActionEvent circuit/commit/RPC 响应失败，验证 durable 补账和唯一计账。
5. 支付确认：票据领取后插件返回 False、抛错、Worker kill -9，验证租约恢复与双击互斥。
6. 风控：DB 有有效 PeerFlood/FloodWait override、Redis key 丢失或冷启动，验证自动回填且不恢复满速。
7. 启动自愈：DB/Redis 在 lifespan 短暂失败后恢复，验证 manager 自动重试和 `/readyz` 状态。
8. LLM 预算：有限额时 Redis/DB 故障必须拒绝；多进程并发不能越过日限额。
9. 歧义探测：同额同 reply anchor 的两笔 payout 不能互相作为送达证明。
10. 鉴权/控制面：恢复码并发单消费、敏感导出 reauth、Worker 环境不含 updater token。

## 7. 一周内可执行的修复顺序

### 第 1 天：止损边界

1. 修 payout 未知异常：进入 send 后一律保留 claim 并转 ambiguous，关闭双付窗口。
2. 修 kill switch：并行确认 Worker、停止 Interaction Bot、拒绝 RPC、冻结补偿扫描，失败非 2xx。
3. 修 callback claim key，恢复同消息多按钮可用性。

### 第 2–3 天：资金闭环

1. 将 payout `sent` 与 `ActionEvent OK` 合并到同一 DB 事务，或先引入 `ledger_pending` durable 状态。
2. `complete=False` 立即转 ambiguous，不得写乐观 OK；歧义 probe 增加 payout_key 唯一证据。
3. 写扫描器补齐历史缺失 ActionEvent，按 `(account_id, payout_key)` 幂等并跑完整资金测试。

### 第 4 天：已付款交互

1. 将 payment confirmation 改为有租约状态机。
2. 为风控 override 增加 DB fallback/rehydrate。
3. 覆盖 False、异常、双击、kill -9、租约超时和 Redis 冷启动。

### 第 5 天：启动与健康

1. 为 supervisor/account bot/interaction bot 建 manager health registry 与退避重试。
2. `/readyz` 纳入关键 manager，updater 等待真正就绪。
3. LLM 配置有限额时 fail-closed；大量账号启动增加 Semaphore + jitter。

### 第 6–7 天：P2 与发布准备

1. 恢复码原子消费、Webhook header-only、敏感导出 reauth、生产 Cookie 安全提示。
2. 剥离 Worker 的 updater token，为有副作用互动建立 Redis 故障策略。
3. 完成全套静态检查、后端测试、前端 typecheck、插件校验与一次临时环境备份恢复演练。

## 8. 明确非问题与已接受实现

- Redis compose 默认 AOF `everysec` 且 `maxmemory-policy=noeviction`；它避免关键状态被静默 LRU 淘汰，但 32 MiB 达上限后会转为写入 OOM，仍需容量监控与关键/缓存分层。
- payout 限额在 DB/Redis 故障时 fail-closed。
- payout 通道固定为 `userbot_reply`，未发现误走 Interaction Bot 的分支。
- payout 在 Telegram side effect 前已有 PostgreSQL `sending` claim；崩溃后的 sending 会进入歧义处理，不会直接盲发。
- 可计账 payout ActionEvent 有 `(account_id, payout_key)` partial unique，能阻止重复计账。
- 单账号 `stop_worker` 在 Redis IPC 失败时仍会本地 terminate/kill；问题在批量/API 确认语义，不是单账号完全依赖 Redis。
- Worker 崩溃退避使用真实等待，稳定窗口后才清 fail count；未发现紧循环重连。
- ZIP 在解压前检查路径穿越、绝对路径、重复成员、成员数、单文件大小、总大小、加密成员和压缩比。
- 远程插件安装在加载 Python 前做静态 manifest/兼容预检；当前“自动更新”是自动检查，不是静默 pull/apply。
- 插件 generation guard 能阻止 reload/disable 后的旧 context 继续注册或执行。
- updater 会拒绝空、过短和占位 token，且 token 与 JWT 已分离。
- TOTP 当前不是“绑定即强制”：UI 明确把绑定密钥与登录验证开关分开，并在完成绑定时同时打开策略；相关测试锁定了关闭策略时不要求 TOTP。这是现行产品契约，不按“二次验证绕过”定缺陷。
- 备份覆盖 PostgreSQL、sessions、installed plugins、plugin repo cache，恢复脚本也覆盖这些对象。
- Trace 使用有界后台队列与批量写，不在常规消息发送热路径同步等待落库。
- 前端 Ledger、Interaction、Logs、Dashboard 已有明确 error 状态，未发现关键页用 `data ?? []` 全面掩盖错误；typecheck 通过。
- 产品模型是个人可信插件；仅“插件可 import os”不构成本轮 P0，当前也未发现未签名远程包默认自动执行的组合利用链。

## 9. 残留风险与上线指标

以下假设需要线上指标或真实环境故障演练才能定量证实：

- 各账号 Worker 的 RSS、数据库连接数和 Telegram 建连峰值；建议按账号数记录启动 p50/p95、FloodWait 和连接失败率。
- LLM 客户端复用的真实收益；建议记录 provider+proxy 维度 DNS/TCP/TLS、TTFT 和请求总时延。
- Ledger 30 天数据规模与 EventTrace label hydration 命中率；建议记录扫描行数、返回条数、查询时延和进程内存。
- Action tap circuit 实际打开次数和 dropped events；在资金修复前应把 `db_dropped_events>0` 作为高优先级告警。
- kill switch 从请求到全部 PID 死亡的总时延；应有 `desired=true`、`observed_stopped/total` 和失败账号列表。
- payment confirmation 失败率、重复点击率和票据过期量；状态机上线后监控 processing lease 超时。

上线接受风险的最低缓解：若资金事务暂时无法立即改造，必须先增加“`PayoutCompensation.sent` 且无 countable ActionEvent”的周期对账告警与人工补账工具；若 kill switch 全链路暂缓，UI 必须显示未确认账号，并同时关闭 Interaction Bot、RPC payout 与自动补偿入口，不能继续宣称全部 Worker 已停止。payout 未知异常删除 claim 的双付窗口不建议接受风险，应直接改为默认 ambiguous。

## 10. 三份报告交叉比对与裁决

本节是在用户明确授权后读取另外两份同版本报告形成的二次裁决。结论不按模型投票，而是逐条回到当前代码与测试验证。

### 10.1 新增并接受

| 其他报告候选 | 裁决 | 综合报告落点 |
| --- | --- | --- |
| payout 非 ambiguous 异常释放 claim 后补偿盲重发 | 接受，P1 Medium；错误文本不能证明副作用未发生 | 新增 P1“payout 发送抛出未知异常时删除 durable claim” |
| callback claim 只含消息 ID，同消息按钮互撞 | 接受，P1 High；当前 key 与调用参数可直接证明 | 新增 P1“callback 跨管道去重键缺少 callback 身份” |
| 风控 override 只读 Redis | 接受，P1 High；DB 是持久写源却无 fallback/rehydrate | 新增 P1“风控 override 丢键后恢复满速” |

| Interaction payout complete=False 仍写 OK | 接受，P2；有 sending 租约自愈，通常不盲重发 | 新增 P2“complete 失败仍立即返回成功” |
| legacy unsigned 默认行为与注释不一致 | 接受为 P3；需管理员主动安装/启用 | 新增 P3“legacy 开关实际放行新 ZIP” |

### 10.2 与原报告重复或已覆盖

| 其他报告候选 | 裁决 |
| --- | --- |
| kill switch API 吞 supervisor 异常 | 与原 P1 kill switch 假成功重复，原报告定级更高且包含前端假提示 |

### 10.3 驳回、降级或作为已知边界

| 其他报告候选 | 裁决与当前代码理由 |
| --- | --- |
| “用户绑定 TOTP 后登录不校验，是二次验证绕过” | 驳回。UI 明确写“先绑定验证器密钥，再打开登录验证；关闭开关不会删除密钥”，绑定验证成功会同时设置 `totp_enabled=true`；测试明确覆盖策略关闭时不要求 TOTP。这是双层策略产品契约，不是静默绕过。可改进 API 原子性，但不能定 P1。 |
| updater 常驻 Docker socket 本身是 P1 | 降为插件/控制面最小权限 P2。利用需要先取得 Web 进程或其 token；token 强度、空值拒绝和私网隔离均存在。风险应收敛，但不等于当前未授权宿主接管。 |
| 未签名插件默认允许即为 P2 | 按个人可信插件模型降为 P3 配置/提示问题。安装和启用需管理员动作，且记录 community trust；真正缺陷是“legacy”注释与新 ZIP 行为不一致。 |
| 静态兼容预检后仍 `exec_module` 是缺陷 | 驳回为产品信任边界。Python 插件被启用后执行顶层代码是当前插件模型本身；兼容预检已在执行前完成。若未来面向公共市场，应另立沙箱威胁模型。 |
| `worker_event` 无订阅者导致当前 session 失效不收敛 | 不定当前 P2。所指 `rate_limited` decorator 在生产代码未使用，当前主 session 失效路径直接写 DB；保留为死代码/误导注释清理项。 |
| Redis `noeviction` 会静默丢关键状态 | 驳回“静默丢失”表述。`noeviction` 是写失败，不是淘汰；但默认 32 MiB 可能 OOM，已作为容量与可用性残留风险保留。 |
| 启动/重连无全局上限必然是 P1 重连风暴 | 降为高优先性能/运维优化。固定退避无 jitter 的同步峰值推理成立，但严重度依赖实际账号数、代理分布与崩溃相关性，需要线上指标支撑。 |
| Event Bus 串行 invoke 是缺陷 | 不作为缺陷。资金和会话动作需要有序；仅纯观察订阅适合受限并发，保留为性能建议。 |
| payout 默认限额 0=不限 | 当前是显式配置语义且故障路径 fail-closed，不定 bug；生产可增加未配置告警或保守模板。 |

### 10.4 交叉比对后的最终优先级

1. 立即修 payout 未知异常默认非歧义的问题，禁止删除已进入网络调用的 claim。
2. 把 kill switch 扩展为覆盖 Interaction Bot、Worker RPC、scheduler 和补偿扫描的统一副作用门闩。
3. 修 callback claim key，避免已付款多按钮玩法卡死。
4. 让 payout complete 与可计账事件形成同一事务/outbox，并处理 `complete=False` 的 ambiguous 状态。
5. 为风控 override 增加 DB fallback/rehydrate；配置 LLM 限额时预算后端 fail-closed。
