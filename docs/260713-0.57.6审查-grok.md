## 1. 执行摘要

TelePilot 0.57.6 已是完整的多账号自动化平台：每账号 Worker 隔离、交互 Bot、Event Bus / MessageOps、payout 限额 fail-closed、发送前 delivery claim、补偿扫描 ambiguous 探测、插件 timeout + 熔断、CSRF、首注 singleton 约束、Redis 默认 `noeviction` + AOF、Postgres 默认 `synchronous_commit=on`。资金与生命周期主路径比早期个人脚本成熟很多。

本轮**未发现可直接判定的 P0（必现双付 / 未授权全站接管 / 无条件 RCE 到宿主机）**。
发现 **3 条 P1**（kill switch 覆盖不全、RPC 旁路 pause、updater 攻击面）、**若干 P2/P3**，以及一组可落地的延迟与扩展性优化建议。

| 级别 | 数量 | 最危险链路 |
| ---: | ---: | --- |
| P0 | 0 | — |
| P1 | 3 | kill switch 未停 interaction bot；worker 已 pause 时 RPC 仍可 payout；updater + docker.sock |
| P2 | 7 | 账本聚合全量拉取、LLM 预算 fail-open、未签名插件默认放行、ledger/ActionEvent 与 claim 一致性窗口等 |

**综合判断：** 核心资金路径（claim → send → complete / ambiguous 接管）设计正确且有测试覆盖；当前最需要补的是 **急停语义完整性** 与 **部署攻击面收敛**，而不是再堆功能。

## 3. 架构简评（基于现状）

### 3.1 优点

1. **账号隔离**：`spawn` 每账号一进程；worker 使用更小的 DB/Redis 池。
2. **资金主路径清晰**：`check_and_consume` fail-closed → `claim_payout_delivery`（DB `sending` intent）→ `send_message` → `complete_payout_delivery`；崩溃后 `sending` 租约到期走 **ambiguous + probe**，避免盲重发。
3. **消息框架**：Event Bus 匹配、插件 `asyncio.wait_for` 超时、连续失败熔断、Trace 与 MessageOps 收口。
4. **生产默认更安全**：Redis `appendonly=yes` + `noeviction`；Postgres `synchronous_commit=on`；updater 强制 `UPDATER_TOKEN` ≥32 且拒绝 `changeme-` 前缀；备份覆盖 sessions / plugins_installed / plugin_repos。
5. **鉴权基线**：首注 `singleton_key` 唯一约束、CSRF double-submit、JWT `pwd_version`、登录限速。
6. **前端关键页**：交互中心与 BotTab interaction mode 有明确 `isError` 分支，不再把失败伪装成“暂无账号”。

### 3.2 系统性残留风险

1. **急停语义分裂**：UserBot worker 可被 stop/pause；Interaction Bot 与部分 RPC 路径不在同一语义下。
2. **资金账本仍是旁路观察**：`ActionEvent` 写失败会降级计数，不等价于财务提交；与 claim 表之间是最终一致而非事务一体。
3. **插件信任模型**：同进程 Python 执行 + 默认允许未签名 ZIP；供应链风险由管理员承担，但默认开关偏松。
4. **Updater 持有 Docker socket**：即使 token 分离，Web 失陷仍可能驱动更新器。
5. **超大模块**：`account_bot_runtime.py` ~9000 行、`loader.py` ~7600 行，审查与回归成本高，易藏旁路。

### 4.2 P1

#### [P1] 全局 kill switch 不停 Interaction Bot，急停语义不完整

- **置信度：** High
- **位置：**
  - `backend/app/api/rate_limit.py`：`post_kill_switch` 仅 `supervisor.stop_running_workers()` / `start_active_workers()`
  - `backend/app/main.py`：interaction bot manager 独立于 supervisor 生命周期
  - `backend/app/services/interaction_bot_runtime.py` / `account_bot_runtime.py`：无 kill switch 订阅
- **机制：**
  打开 kill switch 后 UserBot worker 被停止，但主进程内 **interaction bot polling 继续**。群内关键词/按钮玩法仍会处理；涉及 payout 的 RPC 在 worker 已死后会失败并可能进入补偿队列。关闭 kill switch 后 worker 拉起，补偿扫描可能继续出账。
- **影响：** 用户以为“全局急停”，实际高频互动通道仍在；自动补付在恢复后可能继续动钱。
- **复现思路：** 启用 interaction bot + 可 payout 玩法 → 打开 kill switch → 观察 bot 仍回消息；再关 kill switch 观察 pending 补偿是否自动 replay。
- **修复建议：**
  1. kill switch on：并行 `stop_interaction_bot_manager`（或 per-account pause）+ stop workers + **暂停补偿扫描 / 将自动 replay 门闩关掉**。
  2. kill switch off：按需恢复 bot 与 worker，补偿需人工确认或延迟窗口。
  3. UI 文案明确“急停范围”。
- **回归：** API 级测试：kill switch 后 `is_interaction_bot_running` 为 false；补偿 `enabled` 或 scan 被门闩挡住。

---

#### [P1] Worker 已 pause / 收到 kill switch 广播时，交互 RPC（含 payout）仍执行

- **置信度：** High
- **位置：**
  - `backend/app/worker/runtime.py`：`_listen_cmd` 对 RPC 走 `_should_schedule_background_rpc` **不检查** `paused`
  - `_handle_run_interaction_action_command` → `_run_interaction_userbot_action` 无 pause 门闩
  - 对比：`loader.py` 消息 dispatch 在 `state.paused` 未 set 时直接 return；`scheduler_runtime` 仅在 `paused.is_set()` 时 tick
  - `GCMD_KILL_SWITCH` 仅 `paused.clear()`，**不 stop 进程**
- **机制：**
  若 worker 仍存活且仅被 pause（账号 pause、或仅收到全局 kill 广播而未成功 terminate），interaction bot 仍可通过 Redis RPC 触发 `payout` / `send_message`。消息入站与定时任务停了，**钱相关 RPC 没停**。
- **影响：** “暂停账号 / 急停”与真实资金副作用不一致。
- **复现思路：** 单账号 pause 或 mock 仅 publish `GCMD_KILL_SWITCH` 而不 stop 进程 → 从 interaction 路径发 payout RPC → 仍成功发送。
- **修复建议：**
  1. RPC executor 在执行 `CMD_RUN_INTERACTION_ACTION`（至少 action_type∈{payout, send_message 结算类}）前检查 `paused`；拒绝并返回明确 error_code。
  2. kill switch 广播与 `stop_worker` 语义对齐：优先 terminate，pause 仅作兜底。
  3. 补偿扫描循环同样尊重 kill switch / paused。
- **回归：** pause 状态下 RPC payout 必须失败且不写 sent；resume 后才允许。

#### [P1] Updater 常驻挂载 Docker socket，Web 持有同 token 即可驱动宿主机级更新

- **置信度：** High（架构面；利用需先拿到 Web 或 token）
- **位置：**
  - `docker-compose.yml`：`updater` 挂载 `/var/run/docker.sock`；`web` 注入 `TELEPILOT_UPDATER_TOKEN`
  - `deploy/updater/server.py`：`_authorized` 依赖 header token；启动要求 token ≥32
- **机制：**
  Token 已与 JWT 分离且空 token 拒启（比“空 token 放行”好）。但 **持有 Web 进程环境或能调 Web 更新 API 的攻击者** 等价于可让 updater 通过 socket 执行 compose/更新，接近宿主机 root 能力。插件默认在 worker 进程，通常无该 token，但仍是生产高价值攻击面。
- **影响：** Web 失陷 → 供应链/宿主机 co-opt。
- **修复建议：**
  1. 默认不部署常驻 updater；更新走宿主机 timer / SSH 一次性 job。
  2. 若保留：docker-socket-proxy 最小权限、updater 与 web 网络隔离、mTLS/Unix socket、禁止插件网络访问 updater。
  3. 更新操作二次确认 + 审计不可篡改日志。
- **回归：** 无 token / 错误 token 全拒绝；集成测试不依赖 socket 的 mock 授权矩阵。

### 4.3 P2

#### [P2] Interaction 路径 payout 在 `complete_payout_delivery` 失败时仍报成功，且不主动挂 ambiguous 补偿

- **置信度：** High
- **位置：**
  - `services/interaction/userbot_actions.py`：`marker_ok` 失败只设 `post_send_bookkeeping_failed`
  - `services/interaction/delivery.py`：`ok=True` 时记 `ACTION_EVENT_STATUS_OK`，**不** `enqueue_payout_compensation`
  - 对比 `worker/plugins/loader.py` 同场景会 `_enqueue_compensation(ERROR_AMBIGUOUS_DELIVERY, ...)`
- **机制：** claim 行可停在 `sending`，依赖租约到期后的 ambiguous 扫描；台账可能已显示成功。
- **影响：** 短暂窗口内 UI/台账乐观；与 userbot 插件路径行为不一致。一般不致双付（租约+probe），但运维可见性差。
- **修复：** delivery 路径与 loader 对齐：bookkeeping 失败 → 立即 ambiguous 补偿 + ActionEvent 标记降级状态。

## 6. 性能与建设性优化

原则：**不为降延迟削弱 payout 幂等与 kill switch。**

### 6.1 Quick win（1–3 天）

| 项 | 现状证据 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| RPC/补偿尊重 `paused` + kill switch 门闩 | runtime RPC 无 pause 检查 | 正确性 + 避免急停后仍出账 | 低；需明确错误码 |
| kill switch 停 interaction bot | rate_limit 仅 stop workers | 急停可信 | 中；注意恢复顺序 |
| 生产默认 `plugin_allow_legacy_unsigned_plugins=false` | settings 默认 True | 降供应链风险 | 低；文档说明 |
| LLM client 连接复用 | `llm_client.py` 多次 `AsyncClient()` | 降 TTFT / TLS 握手 | 中；生命周期与代理切换 |
| 插件 invoke 指标（P50/P95、circuit open 次数） | 已有 timeout/circuit，缺统一指标 | 定位慢插件 | 低 |
| 日志/台账大查询加超时与上限提示 | summarize 无 limit | 防拖垮 web | 低 |

### 6.2 Structural（1–2 周）

1. **消息延迟**
   - 保持资金/会话按 `account+chat+session` 串行。
   - 对纯观察订阅（无 action / 只读）在同一事件内有限并发（N=2–4）。
   - Trace 采样：高频群可降 span 细节，失败全量。
   - 热路径避免同步大 ORM；配置缓存 + generation 热更新（已有雏形，审计缓存命中率）。
2. **台账 SQL 化**
   - 金额/方向/chat/recipient 结构化列 + 覆盖索引；`summarize` 不再全表进 Python。
3. **Worker 启动 Semaphore**
   - 全局 2–3 并发 connect，削峰 FloodWait。
4. **ActionEvent 与 claim 同事务边界**（中长期）
   - 至少保证 payout complete 与 ledger 写入同一 DB 事务或 outbox。

### 6.3 Strategic（需基准）

- 10 / 50 / 100 账号：RSS、PG 连接、Redis 连接、启动时间、重连风暴、消息 P95。
- Interaction bot 与 userbot 进程资源拆分评估（是否独立进程池）。
- 第三方插件 subprocess/容器隔离（超出当前个人可信模型时再做）。
- 去掉常驻 docker.sock updater，改为签名 artifact + 宿主机 apply。

### 6.4 延迟相关代码级观察

| 路径 | 观察 | 建议 |
| --- | --- | --- |
| UserBot 入站 | Event Bus 匹配后**串行** invoke；有 30s timeout + 熔断 | 指标 + 慢插件隔离；勿对 payout 并发 |
| Interaction | 主进程 polling + worker RPC；多一跳 Redis | RPC 队列有界（已有 executor）；避免同步重活 |
| 裸直通 | 先于完整总线 | 保持；文档标明无标准 Trace |
| Trace | start/record 在热路径 | 确认有界队列；失败不阻塞发送（抽查 event_trace） |
| 人工拟人化 | send 前 humanize | 结算/payout 路径应跳过（代码中 settlement 有区分，保持） |

## 7. 测试缺口（优先补）

1. kill switch on → interaction bot 全部停止；补偿 scan 不自动 payout。
2. `paused` / kill switch 广播下 `CMD_RUN_INTERACTION_ACTION` payout 必须拒绝。
