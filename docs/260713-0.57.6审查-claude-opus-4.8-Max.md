### 最危险的 3 条链路

1. **急停 + 风控双失效叠加封号链**（P1-4 + P1-5 + P2-5）：`stop_running_workers` 串行且进程终止段无 try，单账号异常中断整批停机；同时风控 override 读路径只查 Redis，Redis 重启后 FloodWait/PeerFlood 收紧静默失效。二者叠加 = 用户以为已急停/已限速，实际 worker 满速发送撞 Telegram 限流窗口 → 封号。
2. **payout 异常误判→盲重发双付**（P1-1）：send 抛非 timeout/network 异常但消息其实已抵达时，交付声明被删、补偿走盲重发 → 同一 payout_key 二次发款。
3. **二次验证虚假安全感**（P1-2）：用户在个人设置启用 TOTP、`/me` 显示 `has_totp=true`，但登录门禁被全局默认关闭的 `totp_enabled` 短路 → 密码即可登录，第二因子从不索要。

## 3. 架构简评（基于现状）

系统边界与心智模型基本吻合：Web/FastAPI → PG/Redis/Supervisor → 每账号 Worker 子进程（Telethon + 插件运行时）。资金侧设计有多层正确防护（详见 §8），交互框架有 RPC 硬超时 + deadline 下发。主要系统性弱点集中在**故障降级路径的 fail-open 取舍**与**批量控制路径的串行/无并发闸门**——正常路径正确，异常/降级路径缺少收敛与兜底。

### P1

#### [P1-1] payout 发送异常被判“非歧义”时删交付声明，补偿盲重发 → 双付
- 置信度：Medium
- 位置：`backend/app/services/interaction/userbot_actions.py:183-191`；重放盲发 `backend/app/worker/runtime.py:1623-1640`
- 机制：`send_message` 抛异常时，`classify_payout_error` 仅按错误文本（timeout/network 关键字）判 `ambiguous`。非歧义即 `release_payout_delivery_claim` 删除 `status="sending"` 声明并 raise，delivery 侧生成全新 `PENDING`（ambiguous=False）→ 扫描走非歧义分支盲重发。若某次 send 其实已抵达 Telegram 却抛非 timeout/network 异常（响应解析/非 FloodWait 的 RPC 后处理错误），SENDING 租约强制歧义探测的安全网被绕过 → 二次发款。
- 影响：资金（重复付款），窄窗口。
- 复现：mock `send_message` 先记录已发消息再抛 `ValueError("bad response")`；断言 claim 行被删、扫描重放再次 send。
- 证据：`if not classification.ambiguous: await release_payout_delivery_claim(...)`；`_is_ambiguous_error` 只匹配 `_TIMEOUT_MARKERS/_NETWORK_MARKERS`（payout_compensation.py:480-486）。**已手工复核 userbot_actions.py:183-191。**
- 修复（fail-closed）：payout send 抛异常时**不按错误文本删 claim**——保留 `status="sending"`，交由扫描 SENDING 分支统一强制 `ambiguous=True` 走探测/人工；仅在网络调用发起前的纯本地校验失败（确定未离开客户端）才允许 release。
- 回归：新增“send 已投递但抛非网络异常”→ 断言不重发、转 ambiguous 探测。

#### [P1-2] 用户启用 TOTP 后登录不校验，除非管理员另开全局开关（二次验证静默绕过）
- 置信度：High（已手工复核）
- 位置：`backend/app/api/auth.py:244-257`；`backend/app/services/auth_login_security.py:300-314`
- 机制：登录 TOTP 门禁为 `if user.totp_secret_enc and not used_recovery and await should_require_totp(...)`，而 `should_require_totp` 第一行 `if not config.totp_enabled: return False`。`totp_enabled` 默认 False 且无 `login_security` 行时返回默认 False。`/totp/enable`+`/totp/verify` 只写 `user.totp_secret_enc`，从不置位全局 `totp_enabled`。二者是独立设置。
- 影响：安全。`/me` 返回 `has_totp=true` 给用户“已开 2FA”的假象，但登录只需密码。
- 复现：新库（无 `login_security` 行）→ enable+verify 成功 → `/me` 显示 has_totp=true → 用户名+密码（无 totp_code）POST login → 直接 `ok=True` 下发 cookie。
- 证据：`should_require_totp` → `if not config.totp_enabled: return False`；enable 流程不触碰全局开关。**已手工复核。**
- 修复：当 `user.totp_secret_enc` 存在时，无论全局 `totp_enabled` 与否都强制 TOTP（把“用户已绑定密钥”视为 always 隐含开启）。比“verify 成功时同步置全局 True”更稳，避免“设置了却不生效”。
- 回归：`totp_secret_enc` 存在 + 全局 `totp_enabled=False` 时，login 不带 code 必须 `require_totp=True`，带错码 401，带对码才成功。

#### [P1-3] 交互 Bot 回调去重键用“按钮所在消息 ID”，同消息多按钮/连点互撞被丢弃（游戏卡死、回调不 answer）
- 置信度：High（已手工复核 key 构造）
- 位置：`backend/app/services/interaction/dedupe.py:24`；`backend/app/services/account_bot_runtime.py:5717`（claim）、`:7799`（callback message_id）、`:5724-5737`（duplicate 跳过）、`:5835`（claim_blocked 返回 True）
- 机制：claim key = `{aid}:{chat_id}:{message_id}:{rule_id}`，不含 `callback_data`/`callback_query_id`/`update_id`/`user_id`。callback 的 `message_id` 取自按钮所附着的 Bot 消息。同一条多按钮消息第一次点击 `SET NX` claim 成功（TTL 钳 60–120s），此后 60s 内该消息所有其他按钮点击 claim 失败 → 走 `cross_channel_duplicate` 分支 `continue`，`claim_blocked=True` 返回 True，既不处理也不 `_answer_callback` → 按钮转圈。成功动作路径不 release，整局锁死。
- 影响：正确性/可用性。任何“一条消息多按钮”或原地 `edit_message` 玩法在一次点击后 1–2 分钟无法响应；财务玩法里后续“加注/发奖”按钮被静默吞掉。
- 复现：发含 `[命中][停牌]` 的消息 → 点“命中”→ 2s 内点“停牌”→ 无响应、回调不 ack。
- 证据：key 不含回调判别维度；TTL 最低 60s；成功后不释放。**已手工复核 dedupe.py:24。**
- 修复：callback 事件 claim key 纳入回调判别维度（优先 `callback_query_id`，或 `callback_data`+`update_id`）；或对 `event_type=="callback_query"` 直接跳过跨管道 claim（Bot API 回调 userbot 收不到，无跨管道重复风险），仅普通消息保留 message_id 去重。
- 回归：覆盖“同消息多回调”（都放行）与“同回调重放”（才去重）两种。

#### [P1-4] 风控 override 读路径只查 Redis，Redis 重启/驱逐后 FloodWait/PeerFlood 收紧静默失效 → 封号
- 置信度：High（已手工复核 get_multiplier）
- 位置：`backend/app/worker/ratelimit/overrides.py:81-89`（`get_multiplier`）；消费 `engine.py:271-276,300-303`
- 机制：`add_override` 双写 DB+Redis，但 engine 每次 `acquire` 只 `redis.get(rlovr:...)`，**从不回落查 DB**。Redis 重启（`REDIS_APPENDONLY` 调成 no）/`FLUSHALL`/LRU 驱逐后键消失 → `get_multiplier` 返回 1.0（异常也吞成 1.0）。启动无“从 DB rehydrate override 到 Redis”的逻辑。
- 影响：资金/安全。FloodWait(×0.7,30min)/PhoneNumberFlood(×0.5,2h)/PeerFlood(×0.0,24h) 在有效期内被静默清零 → 账号按满阈值发送撞 Telegram 限流 → 封号。PeerFlood×0.0（陌生人私聊停用）失效尤其危险。
- 复现：写 override → 重启/清空 Redis（保留 DB）→ `get_multiplier` 返回 1.0，engine 满速放行。
- 证据：`get_multiplier` 无 DB fallback；`acquire` 内 `try: mult=get_multiplier except: mult=1.0`。**已手工复核 overrides.py:81-89。**
- 修复（fail-closed）：`get_multiplier` 未命中 Redis 时回落查 `RateLimitOverride`（`expires_at>now` 取最严）并回写 Redis；或 supervisor 启动 rehydrate 未过期 override。缺失时按 DB 收紧，绝不放行。
- 回归：Redis 冷启动后 override 仍生效；DB 有效但 Redis 缺键时 `acquire` 用 DB 值。

#### [P1-5] Kill switch 批量停机串行且进程终止段无 try → 单账号异常中断整批，DB 显示已停实际仍在跑
- 置信度：High（已手工复核）
- 位置：`backend/app/worker/supervisor.py:672-675`（`stop_running_workers` 串行）、`622-657`（`stop_worker` 进程段 640-652 无 try）；调用方 `api/rate_limit.py:557-565`（`try/except pass`）
- 机制：`stop_running_workers` 用 `for aid: await stop_worker(aid)` **串行**（对比 `stop_all_workers` 用 `gather(return_exceptions=True)`）。`stop_worker` 的 `terminate/is_alive/join` 段不在 try 内，句柄异常抛出即中断循环，其余账号 worker 不再停机。API 又把整段包 `except Exception: pass`，kill switch DB 置 `enabled=true` 但部分/全部 worker 仍连着 TG 发消息/发款。
- 影响：安全/可用性。急停（kill switch 核心用途）失效。
- 复现：让第一个账号 `process.join` 抛异常 → 后续账号不被停。
- 证据：串行循环无 `return_exceptions`；进程段无 try；API 吞异常。**已手工复核 supervisor.py:672-675 + 622-657。**
- 修复（fail-closed）：`stop_running_workers` 改 `asyncio.gather(*(stop_worker(a) for a in aids), return_exceptions=True)`；`stop_worker` 进程终止段包 try/except 保证幂等清理。
- 回归：单账号停机抛异常时其余账号仍被 terminate。

#### [P1-6] 启动/kill-switch 关闭/崩溃重启均无全局并发上限 → Telegram 重连风暴
- 置信度：High
- 位置：`supervisor.py:509-510`（startup 逐个 `start_worker`）、`686-687`（`start_active_workers`）、`_monitor_loop:744-833`（各账号同构退避 `_BACKOFF=[5,10,20,60,300]` 无抖动）
- 机制：启动与 kill-switch 关闭时 `for ac in rows: await start_worker(...)` 无 stagger/信号量，N 账号同时 spawn + `client.connect()`。崩溃场景更严重：Redis/网络抖动致 N worker 同时崩，各自 `next_retry_at` 用相同退避数列 → 同一时刻集体重连 → 对 Telegram 同步连接洪峰。
- 影响：可用性/安全。多账号同 IP/代理同秒重连易触发 Telegram 限流与关联封禁；小机器上同时 spawn 放大内存峰值。
- 复现：50 active 账号 + 一次 Redis 断连恢复 → 5s 后集体重连。
- 证据：无并发闸门；退避表固定无 per-account 抖动。
- 修复（fail-open）：`start_supervisor`/`start_active_workers` 引入并发信号量 + 启动间隔；`_monitor_loop` 退避加 per-account 随机抖动（`wait*(1±0.3)`）。
- 回归：批量重启受并发上限约束；重连时刻分散。

### P2

#### [P2-1] 已发送 payout 记账依赖 delivery 单独发 OK 事件，与 worker 落 sent 分属两事务 → 崩溃/RPC 丢响应时“已发送未记账”
- 置信度：High
- 位置：worker 落 sent `userbot_actions.py:198-205` + `payout_compensation.py:259-307`（`complete_payout_delivery` 只更新补偿行/marker，不写台账）；台账 OK 事件由 delivery 另发 `delivery.py:899-906`；扫描只捞 PENDING/SENDING `runtime.py:1477-1479`
- 机制：实时 payout 成功时 worker `complete_payout_delivery` 置补偿行 `sent` + 写 marker，但不发可计账 ActionEvent；唯一计账来源是 delivery 在 `run_worker_action` 返回后发的 OK 事件。若 delivery 在此之间崩溃或 RPC 响应超时丢失（得到 ok=False），则钱已发、补偿行=sent（扫描不再处理）、台账无 OK 事件（超时路径只写 FAILED）→ 该 payout 对台账完全不可见，无自愈。
- 影响：正确性/资金台账（payout 少计，净盈亏虚高）。
- 修复：在 `complete_payout_delivery` 同事务内幂等写一条可计账 ActionEvent（借 `uq_action_event_countable_payout_key` 去重）；或扩展扫描对 `sent` 且无对应可计账事件的行做对账补 COMPENSATED。
- 回归：“worker 落 sent 后 delivery 未发 OK”→ 断言台账仍含该笔且仅一条。

#### [P2-2] 歧义探测按 (text, reply_to_message_id) 匹配历史消息，非唯一 → 误判“已发送”，跳过真实发款
- 置信度：Medium
- 位置：`backend/app/worker/runtime.py:1685-1724`（`_probe_ambiguous_payout_message`）
- 机制：探测仅以 `文本==target_text` 且 `reply_to==expected_reply_to` 命中即认定送达并标 sent/compensated，不校验消息与本 payout_key 绑定。若在补偿行 `created_at` 之后另有一笔同额、同 reply_to 的合法 payout（同触发消息二次发奖），探测命中那条 → 误判本笔已发 → 标 compensated 却从未发款。
- 影响：资金（收款方少收）+ 台账 over-count。
- 修复：发送文本嵌入可解析的 payout_key 指纹，仅唯一绑定才认定送达；否则转人工核销。
- 回归：“同额同锚点相邻两笔”→ 断言第二笔不被第一笔误判。

#### [P2-3] 第三方 git 插件可读 web 容器内 `UPDATER_TOKEN` → 操纵持 docker.sock 的 updater（越权到宿主 Docker + 全容器日志泄密）
- 置信度：Medium
- 位置：`docker-compose.yml:91-92`（web 注入 token）、`143-150`（updater 挂 `docker.sock` + 私网监听）、`deploy/updater/server.py:568-664`（token 授权 + `/jobs` `/console-logs`）、`worker/plugins/loader.py:4519-4522`（installed 插件在 web 进程 `exec_module`）
- 机制：installed/remote-git 插件在 web 容器 worker 子进程内直接 exec，无 import 限制，可读 `os.environ["TELEPILOT_UPDATER_TOKEN"]`。用该 token `POST updater:8765/jobs` 触发 `prod-update.sh`（重建/DoS），或 `GET /console-logs` 拿 web/pg/redis/updater 全部容器日志（含密钥、连接串明文）。
- 影响：安全（越权到 docker.sock 边界、密钥经日志外泄）、可用性。第三方来源 git 插件（`plugin_repo_service` 支持任意 GitHub 仓库）并非“本人可信”。
- 修复：token 不放 web 通用 env，改独立 secret（file/secret mount，worker 子进程剥离该环境变量）；updater 绑 `127.0.0.1` 或加内网 ACL；`/console-logs` 过 `redact_text`。
- 回归：断言 worker 子进程环境不含 UPDATER_TOKEN；`/console-logs` 对已知密钥脱敏。

#### [P2-4] `worker_event:{account_id}` 频道无订阅者；engine.on_session_invalid 发的 LOGIN_REQUIRED 无人收敛 DB
- 置信度：High
- 位置：`engine.py:502-518`（`on_session_invalid` 仅 publish `event_channel`）；supervisor 仅订阅 `GLOBAL_CHANNEL`（`supervisor.py:716`）；全仓无 `worker_event:` 订阅者
- 机制：`event_channel` 上的 `EVT_STATUS/LOGIN_REQUIRED/PONG/RATELIMIT` 无消费端。engine 的 session 失效处置只发事件、不写 DB，依赖不存在的监听者。主 client 路径（`runtime.py:609,218`）会直接写 DB 收敛，engine 路径不会。缓解：`@rate_limited` 装饰器目前仅 docstring 示例，生产未套用。
- 影响：正确性。若未来经 engine 装饰器捕获失效，账号状态不收敛为 `login_required`，UI 与实际不一致。
- 修复：`on_session_invalid` 直接走 `_handle_login_required` 式 DB 收敛；或 supervisor 增加 per-account event 订阅落库。
- 回归：session 失效经任一路径后 `Account.status==login_required`。

#### [P2-5] Redis 32mb + noeviction 将有界流与关键状态混放；OOM 时限速 evalsha/IPC rpush/发款标记全部写失败
- 置信度：Medium
- 位置：`docker-compose.yml:44-57`（`REDIS_MAXMEMORY:-32mb`、`noeviction`、`mem_limit 48m`）；`buckets.py:152-163`（`evalsha` 仅处理 NOSCRIPT，其余 raise）；`engine.acquire:283-314` 未包裹 `check_and_consume`
- 机制：所有键（`rl:` zset、`rlovr:`、`payout:sent:`、`interaction_rpc:result`、两条 stream）共享 32mb。noeviction 下打满时任何写报 OOM：`buckets.check_and_consume` 的 evalsha 抛非 NOSCRIPT 异常向上抛（`acquire` 未捕获 buckets 层）→ 动作异常；日志 rpush 静默丢；payout 标记写失败被吞。
- 影响：正确性/可用性。内存压力下限速引擎报错打断动作；若运维改 `allkeys-lru`，`rlovr:` 被优先驱逐 → 叠加 P1-4 放大封号。
- 修复：`engine.acquire` 对 `check_and_consume` 异常按保守（queue+固定 wait）兜底；关键键（override/payout）与缓存做逻辑/实例隔离，强约束不可 LRU 驱逐。
- 回归：Redis 报错时限速走保守分支不放行、不抛。

#### [P2-6] 全局 kill switch 到 worker 侧只 `paused.clear()`，worker 仍在线并继续响应被动命令/RPC，非真正急停
- 置信度：High
- 位置：`runtime.py:2164-2170`（worker `_listen_global` 收 `GCMD_KILL_SWITCH.enabled` → 仅 `paused.clear()` + 记日志）
- 机制：kill switch 两条腿——API 本地 `stop_running_workers`（真终止）+ 广播 `GCMD_KILL_SWITCH`。当本地终止抛异常被吞（P1-5），仅剩广播生效，而广播在 worker 侧只暂停主动动作——client 仍连、`_listen_cmd` 仍跑、被动 `CMD_RUN_INTERACTION_ACTION` 等发款类 RPC 仍响应。
- 影响：安全。急停在降级路径下不彻底。
- 修复：worker 收 kill_switch.enabled 时主动断开 client 或拒绝所有副作用 RPC，而非仅暂停主动动作；并修 P1-5。
- 回归：kill switch 开启后 worker 拒绝一切发送类动作。

## 5. 性能与优化建议

| 方向 | 现状证据 | 收益 | 风险 | 改动面 | 优先级 |
|---|---|---|---|---|---|
| **LLM 连接复用** | `llm_client.py` 每调用 `async with httpx.AsyncClient`（P3-2） | 测活/fallback 密集调用省 N 次 TLS 握手，降尾延迟 | key 装配需保持按请求 | 中 | Quick win |
| **交互热路径 config 缓存** | 每条有路由消息一次 PG 读（P3-7） | 高频群省 PG 往返/连接压力 | 缓存失效需 TTL | 小 | Quick win |
| **热路径同步 I/O 移线程池** | dev 录制同步文件写（P3-8）、`_kill_stale_workers` 同步 sleep | 事件循环不被磁盘/清理阻塞 | 无 | 小 | Quick win |
| **worker 内插件 deadline + 降低默认超时** | 默认 30s、未传 deadline、串行 await（见测试缺口） | 慢插件不拖死同账号消息链 | 需与交互链路 15s 对齐 | 中 | Structural |
| **启动/重连并发信号量 + 退避抖动** | 无并发闸门 + 同构退避（P1-6） | 消除重连风暴、降内存峰值 | 无 | 中 | Structural |
| **Redis 关键态与缓存隔离** | 32mb noeviction 混放（P2-5） | 关键状态不被 OOM/驱逐波及 | 需部署调整 | 中 | Structural |
| **观察型插件并发 vs 资金串行** | worker 内分发全串行 | 观察型插件可并发，资金动作保持有序串行 | 需区分动作类型 | 大 | Strategic |

原则：以上优化**不得**牺牲 payout 幂等、kill switch 正确性与限速 fail-closed。

## 6. 测试缺口（最值得补的 10 个）

1. **payout send 已投递但抛非网络异常** → 断言不删 claim、不盲重发、转 ambiguous 探测（覆盖 P1-1）。
2. **TOTP：库中无 `login_security` 行 + 用户有 `totp_secret_enc`** → login 不带 code 必须 `require_totp=True`（覆盖 P1-2）。
3. **同 message_id 不同 callback_data 连续两次回调** → 断言第二次仍 dispatch 且被 answer（覆盖 P1-3）。
4. **override 存 DB 但 Redis 无键** → `acquire` 仍按收紧阈值（覆盖 P1-4）。
5. **kill switch：单账号 `stop_worker` 抛异常** → 断言其余账号仍被 terminate（覆盖 P1-5）。
6. **worker 落 sent 后 delivery 未发 OK** → 台账仍含该笔且仅一条（覆盖 P2-1）。
7. **同额同 reply_to 相邻两笔 payout** → 第二笔进歧义路径不被第一笔消息误判（覆盖 P2-2）。
8. **evalsha 抛 OOM** → `engine.acquire` 走保守排队分支，不放行不抛（覆盖 P2-5）。
9. **kill switch 后 worker 收到副作用 RPC** → 断言拒绝一切发送类动作（覆盖 P2-6）。
10. **慢插件（`await asyncio.sleep(25)`）** → 断言 per-plugin 与整体 dispatch 受合理 deadline 约束。

## 8. 明确非问题（已核实且可接受）

- **payout 硬绑 userbot 通道**：delivery `_on_payout` 恒用 `userbot_reply`、忽略 `send_via`，无 bot 回退（delivery.py:197-206,782-847）。
- **payout 日累计限额**：Lua 原子 check-and-consume + payout_key 幂等，实时与补偿重放不双扣（payout_limit.py:44-63）。
- **可计账 payout 防重复计数**：partial-unique `uq_action_event_countable_payout_key`（action_event.py:76-87）。
- **DB 为 payout 去重真相源**：`complete_payout_delivery` 以 DB `status=SENT` 去重，Redis marker 仅快路径；marker 写失败不导致重复发款（DB 租约只取 PENDING）。
- **dry-run 不实发**：delivery 各 `_apply_*` 在真实发送前短路。
- **无静默 RCE 自更新链**：`auto_update_check_loop` 仅 `git clone` 读 `plugin.json` 标记 `update_available`，绝不自动安装；`update()` 需显式鉴权（remote_plugin_service.py:1310-1367,1694）。
- **updater 空 token fail-closed**：无有效 token 直接退出，`_authorized` 全 403（server.py:40-41,667-669）。
- **zip 配额/穿越防护齐全**：成员数/单文件/总解压/压缩比上限，解压前校验 `..`/绝对路径/加密成员，`extractall` 不还原符号链接，final_dir 二次约束在 installed_root（plugin_install_service.py:173-225,373-379）。
- **git token 主机作用域**：`GIT_CONFIG` extraheader 限定 `http.https://github.com/`，重定向他站不带（plugin_repo_service.py:224-240）。
- **备份覆盖面完整**：迁移前覆盖 DB dump + sessions + plugins_installed + plugin_repos，并 quiesce web 保一致性（backup.sh:123-143）。
- **AI key 不外泄**：`LLMProviderOut` 仅 `has_api_key`；错误路径经 `_safe_error_message`/`diag.redact`；config bundle 导出 `sanitize_bundle_value(drop_sensitive_keys=True)`。
- **Anthropic 空响应**：按 `PROVIDER_LOCAL` 触发 fallback，非死杀链路。
- **手工测活**：不改生产 cooldown，用量以 `source="diagnostic:full-liveness"` 显式记账。
- **改密令旧 token 失效**：deps 层校验 `pwd_v`。
- **前端错误态**：Logs/Dashboard/Extensions 的 `data ?? []` 均有独立 `error` 分支，未把错误伪装成空列表。
- **webhook token**：`secrets.compare_digest` 常量时间校验，账号不存在统一 401。
- **Trace 不阻塞发送**：`record_*/finish_trace` 走 `Queue.put_nowait` + 后台批写，队列满丢弃计数而非阻塞（event_trace.py:481-568）。
- **RPC broker `_pending`**：所有路径经 `finally` 清理，无 inflight 泄漏。
- **单账号崩溃退避**：`_monitor_loop` 首崩设 `next_retry_at=now+5` 后按 tick 检查，正确等待（风险仅在 P1-6 的跨账号同步无抖动）。

## 9. 残留风险与需线上指标才能证实的假设

- **P1-1 双付**触发依赖“send 已投递但抛非 timeout/network 异常”这一窄窗口，其真实发生率需线上 payout 异常分类日志证实。
- **P1-6 重连风暴**的严重度随 active 账号数与共享 IP/代理程度放大，需线上账号规模与 Telegram 侧限流指标佐证。
- **P2-5 OOM** 触发依赖 Redis 实际达到 32mb 上限，取决于日志/流量规模，需线上 Redis `used_memory` 监控。
- **P2-3 供应链**的可利用性前提是用户安装了非自己编写的第三方 git 插件——在纯“个人可信插件”使用下不成立，但产品支持任意 GitHub 仓库装机故保留为 P2。
